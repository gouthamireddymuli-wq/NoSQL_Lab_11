Lab 11.1 – Shard Key Evaluation Matrix

E-Commerce Order Management System · Four candidate shard keys analysed

Objective

Evaluate four candidate shard keys for an e-commerce order management system across four criteria:

Cardinality

Enough unique values to spread data across shards evenly

Distribution

Similar document counts across all shards (no jumbo chunks)

Query Targeting

Queries hit one shard, not scatter-gather across all shards

Hotspot Risk

Not monotonically increasing – avoids write hotspots

✅ Recommendation: hashed(customer_id)

Justification: hashed(customer_id) scores highest across all four criteria. The hash function transforms the customer_id into a uniform value across MongoDB's hash space (2⁶⁴), ensuring every shard receives an equal share of write traffic. Because the shard key still carries customer semantics, queries that filter by customer_id route to exactly one shard (hash lookup) rather than broadcasting. The key is not monotonically increasing, eliminating write hotspots.

Cardinality

Hash space = 2⁶⁴ unique values – effectively infinite chunk granularity

Distribution

MD5/SHA hash randomises chunk ownership – <5% imbalance typical

Query Targeting

Customer-scoped queries always resolve to a single shard via hash index

Activity: MongoDB 5.0+ Resharding
Steps to Reshard a Collection
  1. Connect to mongos and verify the cluster is healthy (sh.status())
  2. Run db.adminCommand({ reshardCollection: "db.col", key: { new_key: "hashed" } })
  3. MongoDB begins cloning data to new chunks in the background while writes continue on the old layout
  4. The balancer tracks a "critical section" at commit time – brief write pause (<2 s typical)
  5. Old chunks are deleted; metadata updated on config servers
  6. Monitor with db.getSiblingDB("admin").aggregate([{ $currentOp: { allUsers: true } }])
Limitations
  • MongoDB 5.0+ required (5.0 introduced resharding)
  • Resharding is resource-intensive: CPU, I/O, and network spike during clone phase
  • Cannot reshard a collection with unique indexes other than _id unless they align with the new key
  • Time proportional to dataset size – large collections may take hours
  • DDL operations (index builds, schema changes) blocked during critical section
  • Abort possible before commit (reshardCollection can be cancelled), but not after
  • In MongoDB 6.0+, refineCollectionShardKey is available as a lighter alternative if the new key is a prefix superset
